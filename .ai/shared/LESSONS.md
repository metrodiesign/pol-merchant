- **Pattern**: pure-logic-first — แยก logic ที่ทดสอบได้ (สูตร/validation) เป็น pure function ในไดเรกทอรีของโปรเจกต์ (co-located กับ logic ที่ทดสอบ) แล้ว unit test เขียวก่อนแตะ UI. — **Why**: ความถูกต้องไม่ปนกับ rendering, ปิด acceptance ที่เป็นตัวเลขก่อน wire UI.
- **Pattern**: /spec-analyze ก่อน design คุ้มเสมอสำหรับฟีเจอร์ที่มี logic — จับ conflict/gap ที่ทำให้ test เขียนไม่ได้ (หน่วย/วิธีปัดเศษ, trigger คำนวณ, empty state, requirement ที่ขัดกันเอง). — **Why**: แก้ที่ requirements ถูกกว่าแก้โค้ดทีหลัง.
- **Pattern**: audit vuln แยก **dev-only chain vs prod-core** ก่อนตัดสิน (ใช้คำสั่งของ package manager ที่ชี้ว่า dep ตัวไหนดึงมันเข้ามา) -> vuln ที่อยู่ใน dev/test chain ล้วน (ไม่ได้ bundle เข้า prod) แก้สะอาดด้วยการ bump major ของ dev tool นั้น; vuln ใน core/transitive ของ prod ให้ flag + ระบุเงื่อนไข resolve, ห้ามรัน auto-fix แบบ force. — **Why**: auto-fix แบบ force มัก downgrade core dep เป็น breaking — เลวกว่าตัว vuln; เหมารวมทุก vuln เป็น "ต้อง fix" จะ downgrade core ทั้งที่ตัวจริงเป็น dev dependency แก้ได้ด้วย bump major. core ที่ยังไม่มี fix ต้องรอ upstream bump. กลไกใน CI: gate เฉพาะ prod attack surface (audit ที่ละ dev dependency, ระดับ high ขึ้นไป) แล้วเปิด tracking issue สำหรับ dev vuln แยก — อย่า gate audit รวม dev dependency ทั้งหมด มันจะแดงทุก PR จาก dev dependency เก่า.
- **Pattern**: รัน long-running server ของโปรเจกต์ผ่าน `rtk proxy <start-command>` เพื่อเห็น raw log ("Ready"/error). — **Why**: rtk hook rewrite output เป็น summary ("Errors: 1 | Warnings: 0") บดบัง log จริง -> เข้าใจผิดว่า server พังทั้งที่ขึ้น 200.
- **Pattern**: cost จริงอ่านจาก ledger `.cost.total_cost_usd` เท่านั้น ห้าม recompute จาก transcript (overcount 1.6-3.7x) — รายละเอียด dedup/การปันส่วน/ข้อจำกัด ledger: `.claude/skills/spec-retro/references/cost-accounting.md`. — **Why**: ระบบคำนวณ cost ให้แล้วผ่าน statusline; recompute เองได้เลขผิดเสมอ.
- **Pattern**: headless `claude -p` buffer output จนงานจบ — pane ว่าง/CPU ต่ำ ≠ ค้าง. ก่อนฆ่า ตรวจ progress บน disk (`git status`, ไฟล์ใหม่, dependency ที่ install แล้ว) ไม่ใช่ดู pane. และ `--permission-mode acceptEdits` ครอบแค่ Edit ไม่ครอบ Bash -> คำสั่ง install/scaffold ติด permission เงียบใน headless (ต้อง `--dangerously-skip-permissions` หรือ `--allowedTools`). — **Why**: เคยฆ่า scaffold ที่กำลังทำงานเพราะ pane ว่าง.
- **Pattern**: หลัง command fail อ่าน output ให้จบก่อนยิงใหม่; แก้ script แล้ว **Read กลับยืนยันการแก้ (โดยเฉพาะ `cd`/path)** ก่อนรัน. error เดิมซ้ำ 2 ครั้ง = หยุด. — **Why**: ลืม `cd` ใน resume-pane ซ้ำ 4 รอบเพราะ re-fire background blind ไม่อ่านผลรอบก่อน + ประกาศ "แก้แล้ว" โดยไม่ได้แก้บรรทัดจริง.
- **Pattern**: `tasks.md` checkbox ขัดกับ git log (commit อ้าง task เสร็จ แต่ checkbox ยัง `[ ]`) เชื่อ **filesystem** เป็น ground truth ก่อนเริ่ม — list ไดเรกทอรี source / build manifest ของโปรเจกต์ดูว่ามี artifact จริงไหม. retrospective-only commit (docs ไม่มีโค้ดคู่) ทำให้ branch ดูคืบหน้าทั้งที่ว่าง. — **Why**: เกือบข้าม task 1 (scaffold) เพราะ log มี commit "task 2-9" แต่ source dir ไม่มีจริง; เชื่อ log = report ผิด/skip บนฐานที่ไม่มี.
- **Pattern**: `git diff --stat` / `--name-only` **ไม่เห็นไฟล์ใน path ที่ยัง untracked** (เคสจริง: source folder ทั้งโฟลเดอร์เป็น `??`) -> retro/handoff ที่ gather "Files Modified" จาก git stat อย่างเดียวจะ **ตกหล่นโค้ดจริง** (เห็นแต่ spec/docs ที่ tracked). เช็ก `git status` (เห็น `??`) ควบคู่ + จำจาก session เอง. — **Why**: รายงานว่า "ไม่มีโค้ดเปลี่ยน" ทั้งที่แก้ component จริง เพราะ stat เงียบเรื่อง untracked.
- **Pattern**: "assemble" task เป็นจุดจับ gap ของ requirement ระดับ section — ก่อนประกอบ cross-check **ทุก section ใน requirement ที่ list ลำดับ/องค์ประกอบ เทียบ component ที่มีจริง + anchor ใน nav data**. เคสจริง: section หนึ่ง (มี REQ ของตัวเอง) ไม่ถูก task ย่อยใด list เลย แต่ requirement ลำดับหน้าต้องมี + nav data มี anchor ของมัน -> assembly เป็นที่เดียวที่จับได้. component ที่ขาด = สร้างเป็น prerequisite ของ assembly (blocker ของ requirement ลำดับหน้า ไม่ใช่ scope creep) แล้ว **flag ดัง + บันทึก gap-fill ใน tasks.md** ไม่แก้เงียบ. — **Why**: decomposition ที่แบ่ง task ตาม verify-modality (typecheck-only vs interactive ใน browser) ทำ section ตกร่อง (section ที่ verify ด้วย typecheck ล้วน แต่ไม่อยู่ใน list ของ task นั้น); ไม่ cross-check ลำดับหน้า = ส่งหน้าขาด section ทั้งที่ทุก task ย่อยผ่านในขอบเขตตัวเอง.
- **Discovery**: multi-session แพงกว่า all-in-one ~30-40% สำหรับ coupled feature — แยก session เพื่อ accuracy เท่านั้น (conscious trade ไม่ใช่ cost win); kernel การตัดสินใจอยู่ที่ `.claude/commands/pane-loop.md` + spec-tasks/SKILL.md, ตัวเลข/วิธีคิด cost ของ multi run: `.claude/skills/spec-retro/references/cost-accounting.md`. — **Why**: เคยเชื่อกลับด้าน (แยก=ถูกกว่า) → default ผิด.
- **Pattern**: PreToolUse hook block (exit 2) ฆ่า compound command **ทั้งก้อน** — setup ที่มัดมาในก้อนเดียวกัน (chmod, mkdir, cp) ไม่รันเงียบๆ. แยก setup ออกจากคำสั่งที่เสี่ยงโดน block, หลังโดน block ให้ไล่เช็กว่าส่วนไหนของก้อนยังไม่ได้รัน, และก่อน commit ตรวจ mode ใน index (`git ls-files -s`) ของ script ทุกตัว. เคสจริง: `hook-bypass-guard.sh` เข้า commit เป็น 100644 เพราะ `chmod +x` อยู่ก้อนเดียวกับ test ที่ destructive-guard block — เจอตอน `git log --stat` แก้ด้วย amend ก่อน push. หมายเหตุประกอบ: hook ที่เพิ่ม/แก้ใน settings.json มีผล**ทันทีกลาง session** (ไม่ใช่ snapshot ตอนเริ่ม) — เหยื่อรายแรกของ guard ใหม่อาจเป็นคำสั่งทดสอบของตัวเอง; test harness ที่มี destructive string ใน argument ให้เขียนเป็นไฟล์ /tmp แล้วรัน ไม่ใช่ inline. — **Why**: เชื่อว่า chmod รันแล้วเพราะอยู่ในคำสั่งที่ "ส่งไปแล้ว" ทั้งที่ hook ตัดก่อน execute → ไฟล์ mode ผิดหลุดเข้า commit.
- **Pattern**: guard/regex hook เขียนเสร็จห้ามเชื่อจนกว่าผ่าน adversarial test เป็นไฟล์ test suite (bypass case + false-positive case ด้วยเคสจริง รันผ่าน stdin JSON) — regex ที่ผ่านตา+ผ่าน test ชุดที่ผู้เขียนนึกออก ยังโดน fresh-context reviewer เจาะได้ 8 ทาง (indented rm, /bin/rm, xargs, git clean แยก flag, combined short flag -nm, hooksPath override) และ false positive ข้ามคำสั่ง (grep -r ตามด้วย rm -f โดน AND ของ flag คนละคำสั่ง). — **Why**: ผู้เขียน test เฉพาะเคสที่ตัวเองนึกออก; reviewer ที่ถูกสั่งให้ "craft bypass แล้วรันจริง" จับ failure mode ที่ผู้เขียนมองไม่เห็นเสมอ.
- **Pattern**: guard ที่มอง command เป็น flat string = fail-open หลายทาง (`\rm`, `"rm"`, `sh -c 'rm -rf'`, `eval 'rm -rf'`, `HEAD:refs/heads/main` ที่ `/` นำหน้า branch) — normalize ลงสำเนา detection-only ที่ไม่ exec (strip backslash/quote) ก่อนหา POS anchor; block rule ที่ชนชื่อคำสั่งคนละโดเมน (SQL `TRUNCATE` vs coreutil `truncate -s`) ต้อง scope ด้วย next-token (ตามด้วย non-dash = SQL); จับ argv ทั้งหมด (`$*`) ไม่ใช่แค่ `$1`. ทุก block rule คู่กับ benign baseline ที่ต้องผ่าน. — **Why**: regex ที่ดูครบยังรอด escape idiom และ over-block coreutil/everyday code; ไม่มี benign baseline = ไม่เห็น false-positive ที่ขวางงานจริง.
- **Pattern**: hardening guard อาจ block การใช้งานชอบธรรมของตัวเอง — tamper-detection (`#9` ห้ามแก้ guard) block คำสั่ง read-only `git config core.hooksPath` (query เปล่า ไม่มี value) ตอน recon เอง; secret-scanner block test fixtures ของตัวเอง (Stripe/`ghp_` sample) จน commit ไม่ได้. แก้: tamper-detect เฉพาะ **write** (มี value / `--unset` / redirect) ไม่ใช่ read; scanner exclude fixtures dir (`.claude/hooks/tests/`); doc-example secret ใช้ค่า placeholder (`<password>` ที่เข้า `<.*>` rule) ให้ทั้งอ่านรู้เรื่องและไม่โดน flag. — **Why**: guard ที่ดักกว้างเกินกลายเป็น false-positive ที่ขวางแม้คนเขียน guard เอง — เจอตอน recon โดน block + commit fixtures โดน scan ตัวเอง.
- **Pattern**: multi-agent edit หลายไฟล์พร้อมกัน → partition ตาม **file-owner** (1 agent = ชุดไฟล์ disjoint ไม่ทับกัน) กัน write-conflict โดยไม่ต้อง worktree; แต่ agent ที่อ่าน shared tree กลางคันเห็น edit ที่ยังไม่เสร็จของกลุ่มอื่น → per-agent test count มั่ว. เชื่อ integration verify ที่รัน **หลังทุกกลุ่ม land** เท่านั้น (fullsuite ที่รันก่อน repair = stale). — **Why**: builder verify รายงาน test แดงจาก edit ครึ่งทางของกลุ่มอื่น ไม่ใช่ bug ตัวเอง; ตัดสินจาก snapshot กลางคัน = ตื่นตูม/พลาดของจริง.
- **Pattern**: slash-command/skill ที่ prose ฝัง expected repo/owner (เช่น `/spec-sync-github` คาด `metrodiesign/spec-driven-development`) — ยืนยัน remote จริงด้วย `git remote -v` ก่อนเขียน external resource (issue/PR) เสมอ แล้วใช้ค่าจริง; เคสจริง remote = `metrodiesign/pol-admin` ต่างจาก default ใน skill. — **Why**: เชื่อ default ของ skill = สร้าง issue ผิด repo หรือ fail; ground-truth จาก git ถูกกว่าตัวอย่างใน prose.
- **Discovery**: GitHub MCP `issue_write` `method=create` + `state:"closed"` **ไม่ปิด issue ตอนสร้าง** — issue เกิดเป็น open เสมอ (state ถูกเพิกเฉยตอน create); ต้อง `method=update state=closed` แยกอีกรอบ. หลัง sync ที่ควรมี issue ปิด ให้ verify ด้วย `gh issue list --state open` อย่าเชื่อ manifest/ค่าที่ตั้งใจ. — **Why**: /spec-sync สร้าง sub-issue ด้วย state=closed คิดว่าปิดแล้ว แต่เปิดค้างทั้งชุด (manifest=closed แต่ GitHub=open ไม่ตรง) เพิ่งจับได้ตอน list. (เกี่ยว: task-gate บังคับบรรทัด `viewports:` ใน Evidence ของทุก task ที่ mark `[x]` แม้ logic-only — ใส่ `n/a — logic-only`.)
- **Pattern**: ก่อน `commit + pr` รอบถัดไปบน feature branch เดิม เช็ก `gh pr view <n> --json state` ว่า PR ยัง **OPEN** — ถ้า MERGED ไปแล้ว commit ใหม่ที่ push ตามจะ **ค้างลอย** (ไม่อยู่ใน PR ไหน ไม่เข้า base) ต้องเปิด PR ใหม่. `gh pr create` ที่ตอบ "a pull request already exists" ไม่ได้ยืนยันว่า PR ยังเปิด. ลบ remote branch (`git push origin --delete`) โดน destructive-guard block ("confirm with a human first") — ให้ user รันผ่าน `!` prefix หรือ GitHub UI, อย่า bypass. — **Why**: รอบนี้ push manifest+retro ตาม PR ที่ merge ไปแล้ว → 2 commit stranded ต้องตามเปิด PR เก็บ.
- **Pattern**: reference screenshot ที่ user ส่งมาอาจถ่ายจาก **หน้า/component อื่น** (drawer, อีก route) แล้วต้องการให้เอา *style* ไป apply ที่ปลายทางอีกตัว — ก่อน edit ยืนยันว่า "แก้ตัวไหน" ให้ชัด (ถ้า image ไม่ระบุไฟล์ + มีหลายตัวที่ใกล้เคียง ให้ถาม/สะท้อนความเข้าใจก่อน). — **Why**: รอบนี้ตีความ reference เป็น "แก้หน้าที่ภาพถ่ายมา" เลยแก้ `role-read-view.tsx` แทน checkout modal ต้อง revert; ambiguity เรื่อง target component ราคาถูกถ้าถามก่อน แพงถ้าแก้ผิดไฟล์แล้วย้อน.
- **Pattern**: ผล Workflow/subagent review เชื่อไม่ได้ถ้ามี `<failures>` — verifier ที่ตายกลางทาง (spend-limit / terminal error) คืน verdict null, partition แบบ `f.verdict?.isReal` ตีเป็น falsy แล้วตกเข้า `rejected` เงียบๆ ปนกับ finding ที่ถูก refute จริง. ก่อนเชื่อ rejected/confirmed: นับ `<failures>` เทียบจำนวน verifier ที่ควรรัน; verifier ไหนตาย ให้ re-verify finding นั้นด้วยมือกับไฟล์จริง อย่าถือ rejected = ไม่ใช่ปัญหา. ออกแบบ harness ให้ verdict ที่หายไป = "ยังไม่ตัดสิน" (ไม่ใช่ rejected) จะปลอดภัยกว่า. — **Why**: เคส Tier 4 review verifier 16/17 ตาย แต่ผลส่ง `confirmed:1, rejected:16` ดูเหมือนผ่านเกือบหมด ทั้งที่ rejected ส่วนใหญ่ไม่เคยถูกตรวจ — ถ้าเชื่อตามจะ ship 7 bug จริง.
- **Pattern**: task-gate (`gate-task.sh`) ตอน mark `[x]` ต้องมีบรรทัด `Evidence:` ใน region ของ task นั้น (จาก `- [x]` ถึง checkbox ถัดไป) ที่ awk จับด้วย `^\s*Evidence:` — บรรทัดต้องเป็น **plain indented ไม่ใช่ markdown bullet**: `  Evidence: ...` ผ่าน, `  - Evidence: ...` **ไม่ผ่าน** (prefix `- ` คั่นหน้า label). ค่า `n/a` ผ่าน (เฉพาะ `n/a (write path)` ถูก reject). gate รัน `npm test` (auto-detect `"test"` script) เป็น code-green ก่อนเช็ก Evidence. — **Why**: เสีย 2 รอบ — เขียน Evidence เป็น bullet (awk ไม่ match) + เข้าใจผิดว่าต้องมีคำว่า "viewports:" จริง ๆ gate ขอแค่ label `Evidence:` + ค่า non-trivial.
- **Pattern**: destructive/branch guard (PreToolUse) ตัดสินจาก **state ก่อนคำสั่งรัน** — `git checkout -b feat && git commit` ยังโดน block เพราะ guard เห็น branch = `develop` ตอน hook fire (ก่อน checkout มีผล). แยก `git checkout -b` เป็นคำสั่งแรก แล้ว `git commit`/`push` คำสั่งถัดไป. — **Why**: guard อ่าน current branch ตอน hook ไม่ใช่หลัง compound resolve; มัด checkout+commit ก้อนเดียว = self-defeating (ต่อยอด "PreToolUse block ฆ่า compound ทั้งก้อน").
- **Pattern**: read-only view ที่ clone จาก form view — ห้าม import component ของ module อื่น (เช่น CheckoutCard เข้า transaction view) เพราะนำ "use client" contamination + cross-module coupling มาด้วย; สร้าง local helper ขนาดเล็กที่ mirror visual เดียวกันแทน. — **Why**: Server Component ใน Next.js App Router สูญ server-render ทันทีที่ import "use client" component จาก module อื่น; local helper ลบได้เลยไม่มี coupling ข้าม module.
- **Pattern**: ก่อนสร้าง field helper สำหรับ read-only view ถามก่อนว่า visual style ต้องการ **input-box** (border + bg-grey) หรือ **plain bold text** เพราะกระทบทุก field ใน component. — **Why**: สร้าง ReadField input-style ไปทั้ง component แล้ว user ขอเปลี่ยนเป็น plain text ทุก field ในรอบเดียวกัน; ถามตอนออกแบบ helper ถูกกว่า refactor ออกทั้งหมด.
- **Pattern**: CI red ≠ ความผิดของ PR เราเสมอ — check engine ที่ loop ทุก spec/target (เช่น spec-trace ทุก feature dir) จะ red ทุก PR เพราะ **sibling ที่พังอยู่ก่อน**. ก่อนรับเป็นของตัวเอง/แก้: `git diff <base>...HEAD -- <failing-area>` ว่าง = pre-existing (ดู develop HEAD ว่าก็ red ไหม). user ที่บอกว่า "merged แล้ว" อาจเข้าใจผิด — verify `gh pr view <n> --json state,mergedAt` (OPEN + mergedAt null = ยังไม่ merge, อาจติด required check แดงนี้). — **Why**: รอบนี้ user แจ้ง "merge #49 เสร็จ" แต่จริง ๆ OPEN ติด CI `producer-management` spec-trace ที่ pre-existing บน develop (ไม่เกี่ยว PR เลย); เกือบไปแก้ spec คนอื่น/เข้าใจผิดว่า auth regress.
- **Discovery**: Next.js Turbopack dev server zombie — process alive + port bound + log ว่าง + serve HTTP 404 ทุก route แต่ body เป็น HTML จริง. diagnose: `curl -i <url>` ดู body; 404 ที่มี HTML body = zombie (ไม่ใช่ route ไม่มี). Fix = `kill <pid>` แล้ว restart สด. — **Why**: อาการ 404 ทุก route ดูเหมือน routing/config ผิด ทั้งที่โค้ดถูก; `curl -s -o /dev/null -w "%{http_code}"` คืน 404 เหมือนกันทั้งสองเคส — ต้อง `curl -i` ดู body แยกให้ได้.
- **Pattern**: integration guide ของทีมอื่น (FE adapter doc) อาจไม่ครบ contract — cross-check **backend source** เส้น error/redirect/callback (ไม่ใช่แค่ happy path) ก่อนประกาศ done. เคสจริง: `admin-fe-integration.md` ไม่ระบุ route `/login-error` + reason codes (อยู่ใน `AdminAuthOptions.ErrorPath`/`AdminLoginService.DenyAsync`) → เจอ 404 ตอน live E2E จริงเท่านั้น. — **Why**: guide เขียน happy path ครบ แต่ deny/error path ตกหล่น; ถ้าไม่ทดสอบจน backend deny จริงจะไม่เจอ route ที่ขาด.
- **Pattern**: แยก concern ที่ 2 ออกจาก PR ที่เปิดค้าง (base ยังไม่ merge เข้า develop) และ **แชร์ไฟล์กัน** -> branch concern-2 ออกจาก branch ของ PR แรก (ไม่ใช่ develop) แล้วเปิด PR base = branch แรก (stacked); พอ PR แรก merge -> retarget base เป็น develop. — **Why**: branch ออกจาก develop ตรงๆ ตอน commit ของ PR แรกยังไม่อยู่ใน develop = ไฟล์ที่แชร์กันคนละ base -> conflict ต้อง resolve เอง. stacked = zero conflict, linear, GitHub retarget base ให้เองตอน parent merge.
